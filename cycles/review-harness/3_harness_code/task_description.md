# Описание задачи: реализация технической обвязки (код)

Артефакт — код обвязки и его тесты:

- `src/review_harness/` — пакет: errors, runcat, machine_profile, launcher,
  subproc, critic, cycle, gates, liveness, profile_sync, cli;
- `tests/harness/` — тесты пакета;
- строка регистрации пакета в `pyproject.toml`.

Код обязан реализовывать финализированную спеку
`docs/design/2026-09-01_review_harness_spec.md` (подтверждённый интент,
финализирован 2026-09-01) — она и есть источник тезисов ниже. Тексты пары
(`docs/review/critic.md`, `docs/review/development.md`) код носит как данные
и не меняет.

Авторство описания (круг 1): тезисы — пересказ разработкой спеки и её же
рабочих решений реализации; рабочие решения перечислены в границе предмета.
Описание предъявлено оператору на входных воротах до первого прохода.

## Тезисы

Отказы и входы:

1. Отказ обвязки невозможен без причины и следующего действия — тип отказа
   не позволяет их опустить, пустые поля отвергаются на конструкторе;
   дисковые ошибки И битые кодировки на ЛЮБОМ чтении и записи файлов
   обвязки (каталог, журнал ворот, кэш и буфер профиля, сопроводиловка,
   артефакты снимка, файлы CLI) — тоже отказ обвязки, не сырой traceback; структурные проверки повреждённых
   файлов — явные ветки, переживающие python -O (assert-гарантий нет).
2. Модель критика — обязательный явный вход создания прогона; пустая
   модель — отказ.
3. Пустой проход критика — отказ («не ноль находок, а отсутствие текста»).
   Транскрипт критика склеивается из ОБОИХ потоков, stderr-первым: шапка
   codex печатается в stderr (готовое знание проекта — isolation.py
   аудиторного жанра), и аттестация по одному stdout аннулировала бы
   каждый честный проход. Пустота меряется по содержательной части
   разбора реального формата (шапка между разделителями, эхо промпта
   после «user», ответ после маркера «codex») — шапка и эхо ответом не
   являются; пустая ошибка инструмента называется дефектом в отказе.
   Байты, не являющиеся UTF-8, сохраняются видимыми эскейпами в тексте,
   а ТОЧНОЕ побайтовое свидетельство ложится raw-файлом рядом со стримом
   (текстовые эскейпы неоднозначны: байт 0xFF и четыре символа «ÿ»
   неразличимы).
   Отказ обвязки не рапортует «роль остановлена», если добитие дерева не
   подтвердилось, — это называется в тексте отказа.

Транспорт:

4. Каталог прогона создаётся с описанием, сопроводиловкой и метаданными;
   создание поверх непустого каталога — отказ (защита живого прогона);
   пустое описание отвергается; каталог внутри репозитория принимается
   только git-игнорируемый — это проверяет сама обвязка, а не дисциплина
   вызывающего, и та же проверка стоит на буфере досылки — с той же семантикой
   гигиены (пивот оператора: внутри репозитория допустим под игнором). Приватность
   определена решением оператора (круг 9, дословно: «в игнор она — чтобы
   репу не засирать»): правило git-игнора — ГИГИЕНА дерева репы, а не
   оборона; злонамеренный коммитер на личной машине — вне модели угроз
   оператора, а угроза публикации закрыта уровнем выше — рабочая репа не
   публикуется вовсе (решение R1.1: публикация отдельной чистой репой).
   Каталоги прогонов живут в репе под игнором; уже построенные страховки
   остаются как есть (стримы ролей в системном temp, проверка приватности
   в самой долговечной записи, ежесекундный тик надзора, privacy-отказ
   убивает дерево) — но НОВЫХ укреплений этот класс не требует, и
   секундное окно после смены .gitignore дефектом не является —
   частичный вывод критика не успевает лечь в публикуемое дерево до
   отказа; проверка стоит не только при создании:
   каталог или буфер, ставший отслеживаемым между кругами, отвергает
   запись. Коды
   git check-ignore различаются: «отслеживается» — только код 1; прочие
   отказы git (чужой владелец, обрыв) — «проверка не выполнилась», с
   починкой git-доступа в тексте отказа, не с советом про .gitignore.
5. Проход критика записывается дословно — байт в байт, без заголовков и
   подстрижки обвязки (метаданные — в соседнем файле) — и немедленно, со
   сбросом на диск (fsync); попытка записать исходы раньше прохода — отказ;
   записанный проход не переписывается никогда. Метаданные круга (снимок
   версии артефакта — хеши содержимого + git-голова — и версия профиля
   подачи) ложатся РАНЬШЕ прохода одним состоянием: проход без метаданных
   не существует ни в какой момент, а мета обязана быть ПОЛНОЙ — версия
   подачи, git-голова и снимок, покрывающий РОВНО артефакты прогона плюс
   описание и сопроводиловку (словарь с фиктивным ключом полнотой не
   является); git-голова — настоящая, либо явное «вне-git» для прогона вне
   рабочей копии; заглушка ошибки полноту не проходит, ошибка git при
   существующей репе — громкий отказ; проверяется на записи, чтении и
   восстановлении; пустой проход не записывается, а обрезанный до пустоты
   файл прохода ломает восстановление громко; продолжение разбора без полной меты — громкий отказ,
   не разбор вслепую; изменение артефакта после прохода
   объявляется вслух при продолжении.
6. Состояние цикла (модель, круги с проходами и исходами, текущий круг,
   входные ворота, висящие развилки) восстанавливается из одних файлов
   каталога; чужой или повреждённый каталог — громкий отказ, не сырой
   traceback; метаданные проверяются по типам (строка «"false"» не
   притворится булевым), посторонние файлы не роняют восстановление,
   обязательность описания и сопроводиловки проверяется; исходы без
   прохода — повреждённое состояние и отказ восстановления (осиротевший
   файл исходов не выдаст несостоявшийся разбор за состоявшийся), и
   пустой файл исходов при восстановлении — тоже отказ (активный путь
   пустое не пишет — значит, повреждение); история кругов обязана быть
   непрерывной 1..N — потерянный промежуточный круг это повреждение
   истории решений, а не повод продолжить с максимального номера; исходы
   образуют ПРЕФИКС истории (исходы круга 2 без исходов круга 1 — набор,
   невозможный на здоровом пути, и отказ). Перезапуск
   незавершённого круга продолжает разбор с записанного прохода, не
   переигрывая критика. Номер круга ведётся для восстановимости, потолков
   нет — и двузначный шаблон имени не создаёт фактического потолка на
   сотом круге.

Запуск и профили машин:

7. Профиль машины живёт на пути запуска; у агента есть штатная запись
   (save); отсутствие профиля — отказ, называющий, как его создать.
   Команда критика обязана нести {model}, команда разработки — {run_dir}
   и {round}; иначе явно выбранная модель или пути круга молча подменились
   бы умолчаниями инструмента; отсутствие маркера — отказ на валидации
   профиля.
   Сопроводиловка доставляется СОДЕРЖИМЫМ через stdin (позиционный «-»):
   для codex exec позиционный аргумент — текст инструкции, путь файла
   инструкцией не является; {launch_note} в argv легален ТОЛЬКО под
   break-glass (тестовые роли), профиль без «-» и без {launch_note} —
   отказ; заготовка profile-init рождается сразу в безопасной форме
   белого списка.
   Профиль несёт и ОКРУЖЕНИЕ запуска (env; спека: «команда, окружение,
   песочница») — роли стартуют с ним поверх окружения обвязки, а не
   наследуют случайную оболочку; проверка исполнимости ищет команду в ТОМ
   же окружении (профильный PATH), а значения env типизированы строго
   строками. ВСЕ поля
   профиля проверяются по типам во время исполнения: строковое «false»
   в break-glass не притворится булевым и не откроет пишущего критика.
8. Окно распознавания смерти заземлено наблюдённым обрывом среды и строго
   положительно (отрицательное или нулевое окно убивало бы живую роль
   первой проверкой): окно меньше наблюдённого — отказ; наблюдение без записи происхождения — отказ.
9. Команды обеих ролей проверяются на исполнимость реальным поиском
   исполняемого файла — это обязан быть ФАЙЛ с правом исполнения, каталог
   исполнимым не считается; пустая команда — отказ (проверка не бывает
   тихой).
10. Лаунчер пишется с переносами целевой платформы (CRLF для Windows) и
    пробуется реальным интерпретатором; упавшая проба = «не доставлен»,
    полезная нагрузка не запускается. Класс скобки cmd закрыт статикой
    генерации (неэкранированная скобка в теле — отказ; динамически cmd
    класс не ловит — молча терпит лишнюю скобку, проверено вживую
    2026-09-01) и структурой (тело вне скобочных блоков обвязки); для sh
    тело разбирается по-настоящему (sh -n).

Живучесть и цикл:

11. Время уведомления берётся из кэша профиля оператора (notify-within);
    его отсутствие — громкий отказ с указанием, как добавить предпочтение
    в граф. На старте круга называются окно, время уведомления и их сумма.
12. Молчание ОБЕИХ ролей наблюдается окном машины: повисшая роль признаётся
    мёртвой, процесс убивается ВМЕСТЕ с деревом дочерних процессов (иначе
    порождённый ролью помощник продолжал бы работать после объявленной
    смерти), полученный вывод цел в файле, отказ называет следующее
    действие. Гарантия дерева СТРУКТУРНАЯ, не по трубам: роль живёт в
    Job Object (Windows, kill-on-close) или своей группе процессов (POSIX),
    и завершение роли — любым исходом — закрывает всё дерево, включая
    помощника с DEVNULL-трубами, невидимого слежке за выводом. Гарантия
    fail-closed: недоступный Job Object останавливает запуск роли, а не
    ослабляет его; на Windows роль рождается приостановленной и оживает
    только после присоединения к джобу (потомок не ускользает в окно до
    Assign); идентификатор группы снимается при старте (после reap
    родителя его не спросить); упавшее открытие файла стрима убивает уже
    запущенный процесс, не оставляя его без надзора; смерть дерева
    подтверждается и на УСПЕШНОМ пути — неподтверждённое добитие =
    отказ, а не молчаливый успех; на POSIX идентификатор группы известен
    ПО ПОСТРОЕНИЮ (setsid: pgid = pid роли) — гонки с быстрым выходом
    родителя нет, а ошибка killpg не выдаётся за подтверждение; оба потока
    роли стримятся в partial (диагностика stderr цела на диске, как
    обещает отказ), отказ записи стока — отказ роли с убийством дерева,
    а запись стока живёт вне замка монитора (зависший диск не ослепляет
    надзор за молчанием);
    неподтверждённая смерть дерева называется в тексте отказа. Признак жизни — любые байты в любой из труб, не законченные
    строки: роль, стримящая токены без перевода строки, жива.
12а. Долговечность переименования включает fsync каталога файловой системы
    на POSIX (внезапное отключение питания не возвращает старый файл).
13. Цикл без ручной переноски: критик запускается командой профиля, проход
    немедленно пишется в каталог, разработка возобновляется headless-командой
    профиля с путями каталога; отсутствие исходов после разбора — отказ,
    указывающий, что проход цел; исходы, записанные headless-ролью обычным
    способом, цикл пере-долговечивает своим API (fsync + приватность), и
    ЗАВЕРШЁННОСТЬ круга существует только после долговечной отметки самой
    обвязки — после всех её проверок (запросы к оператору обслужены,
    повторная подача отвергнута): файл исходов от разработки сам по себе
    круг не закрывает, обрыв до отметки оставляет круг идущим и перезапуск
    его доводит, не обходя ворота.

Ворота:

14. Вопрос оператору и его дословный ответ фиксируются в каталоге немедленно;
    у API ворот нет ветки отказа оператору; «уверен?» задаётся не больше
    одного раза и ответ исполняется; развёрнутое утвердительное слово
    оператора («Финализацию принимаю», «да, финализируй») распознаётся,
    отрицание доминирует — включая морфологическое, но только над
    утвердительными основами («точно нет», «несогласен» — отказ;
    «да, немедленно финализируй», «непременно согласен» — согласие;
    идиомы «не возражаю» и «не против» — русское согласие, не отказ), а нераспознанный ответ не
    решается за оператора ни в какую сторону — обвязка честно переспрашивает,
    записывая все обмены — включая ПРОМЕЖУТОЧНЫЕ нераспознанные ответы,
    журналируемые немедленно с ТЕМ текстом, на который оператор фактически
    отвечал (после уточнения — текст уточнения); состояние ворот ПЕРВИЧНО, журнал gates.md —
    производная: дословный ответ входных ворот ложится одной долговечной
    записью вместе с флагом и фактическим текстом вопроса (в run.json),
    ответ пачки — в JSON ответов до журнала; обрыв между записями не
    рождает повторного вопроса оператору, а упавшая после флага запись
    журнала дочинивается из состояния при следующем входе — журнал не
    остаётся неполным навсегда.
    Входные ворота читают ответ ТЕМ ЖЕ разборщиком
    («Да, подтверждаю описание» — согласие, а не строковое несовпадение).
    Входные ворота держит сама обвязка:
    первый проход критика не запускается, пока подтверждение описания
    оператором не записано; неподтверждение — остановка с его дословным
    ответом.
15. Запросы разработки к оператору доставляются через ворота, ответы
    записываются и возвращаются в цикл, после чего разбор довершается;
    движение по вопросу стоит до ответа. Файлы запросов и ответов —
    покруговые (ответ одного круга нечитаем как ответ другого); ответы
    ложатся долговечно РАНЬШЕ удаления запросов — обрыв между шагами не
    оставляет «спрошено и потеряно», и КАЖДЫЙ ответ пачки долговечен
    немедленно — падение на втором вопросе не повторяет первый, частично
    отвеченная пачка продолжается с неотвеченного. Висящая развилка
    прошлой сессии обслуживается ДО передачи управления разработке;
    полностью отвеченная пачка не переспрашивается, а ЧАСТИЧНО отвеченная
    при восстановлении честно числится висящей — полнота меряется
    ИДЕНТИЧНОСТЬЮ вопросов, не количеством ответов; повторная подача запросов
    после записанных ответов круга — отказ (проверяется и после довершения
    разбора); элементы файлов
    запросов и ответов проверяются структурно (question/answer) — порча
    даёт отказ с причиной, не сырой KeyError.

Сырьё профиля оператора:

16. Половинки пар обмена не пишутся — неполная пара отвергается в обе
    стороны (реакция без развёртки И развёртка без реакции; отсутствие
    реакции записывается явным текстом), и
    восстановленная из файла пара проходит ту же валидацию, что и
    принимаемая (буфер не дошлёт в граф то, что append отверг бы); буфер
    досылки долговечен (fsync) и восстанавливается новой сессией из файла.
17. Досылка убирает каждую досланную пару из буфера долговечно СРАЗУ после
    её успеха (окно повторной отправки — одна пара, не весь буфер); первая
    неудача останавливает досылку с сохранением хвоста и громким отказом
    «не потеряно, повтори». Пара пишется по закрытии обмена; реакция без
    развёртки отвергается.
18. Неоднозначные сигналы хранятся неоднозначными (разметка допускает
    «не знаю» и дообозначается при пересборке).
19. Кэш профиля переписывается только при смене контент-адресуемой версии;
    версии сравниваются точным равенством, не вхождением подстроки; версия
    кэша, по которой шёл круг, фиксируется в метаданных круга, а смена
    версии между проходом и продолжением дописывается в метаданные и
    объявляется вслух; кэш без строки версии — отказ, не заглушка.

Вычитание и приёмка:

20. Кода реестров покрытия, потолков кругов и вердиктов в пакете нет;
    команд CLI — шесть (create, round, cycle, status, profile-check,
    profile-init), и каждое действие, на которое отсылает текст отказа,
    существует.
20а. Обвязка ВЕДЁТ цикл, а не только круг: правка артефакта после разбора
    (снимок изменился против того, что видел критик) автоматически
    запускает следующий полный проход без участия оператора; отсутствие
    правки останавливает цикл — обвязка перестаёт крутить и ждёт слова

21. Тесты покрывают перечисленные обязанности, включая отказные ветки;

Только-чтение критика:

22. Критик не пишет никогда, и это обеспечивают два перенесённых из
    старого контура слоя: структурный страж команды (закрыт по умолчанию —
